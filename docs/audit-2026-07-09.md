# RadioWave Audit — 2026-07-09

Status: 2026-07-09 — post 1.0.12 (targetSdk 36)

Multi-agent static code review across `core-player`, `core-network`, `auto`, `core-cast`,
`core-database`, `core-data`, `core-model`, all `feature-*` modules, the `app` module, build
config, and CI workflows, plus a competitive feature-gap review. No Android SDK emulator/device
was available for this pass, so this was a static/manual code review backed by real compile
(`gradle build`), full unit test run, and lint — not a runtime/UI smoke test.

## Fixed (branch `fix/audit-2026-07-09`)

- **[critical]** `MIGRATION_1_2`/`MIGRATION_2_3` defaulted `stationName`/`streamUrl` to `''`
  instead of backfilling — any favorite/recent that predated the v1→v2 or v2→v3 upgrade lost
  its name and playable URL. New `MIGRATION_3_4` repairs what it can from the stations cache
  and removes unrepairable rows.
- **[medium, security]** `favicon` URLs (community-editable API data, same trust level as
  `streamUrl`) reached the media notification / Android Auto / Cast SDK / Coil image loader
  without the http/https-only scheme check `streamUrl` already had — closed at all four sinks.
- **[medium]** `toggleFavorite` had a non-atomic check-then-act race; wrapped in a
  `@Transaction` DAO method.
- **[low]** Cover art negative-cache was a no-op (`Map.get` can't distinguish "not cached" from
  "cached miss"), so every track with no artwork re-hit the iTunes API on every play.
- **[low]** `getFavorites()`'s fallback mapper dropped `addedAt`.
- **[medium]** Portrait fullscreen player showed the LIVE indicator during an active error
  (landscape already guarded this).
- **[medium]** Sleep timer lived in Activity Compose state — lost if the app was swiped from
  Recents while the foreground service kept streaming. Moved to `RadioPlayerManager`
  (process-lifetime singleton).
- **[medium]** Error banner's Retry button had no debounce; added a 1.5s cooldown.
- **[medium]** Touch targets under 48dp in the fullscreen player header/controls, mini player,
  and Browse grid's favorite toggle (Favorites list already had this fix).
- **[medium, CI]** GitHub Actions pinned to floating tags across all three workflows; pinned to
  commit SHAs.
- **[low, CI]** Shell-injection path in `manual-build.yml`'s `gradle_task` workflow_dispatch
  input; passed through env var + character allowlist instead of direct interpolation.

## Deferred (tracked in ROADMAP.md, not fixed this pass)

- Android Auto: distinguishing "network error" from "genuinely empty" in the browse tree
  (`RadioWaveAutoService`'s `runCatching { ... }.getOrDefault(emptyList())` pattern collapses
  both to the same "no stations available" message) — moved to ROADMAP under Android Auto
  expansion, not fixed here since it touches the car-facing browse tree broadly and deserves
  its own pass rather than a quick patch.
- `PARTIAL_WAKE_LOCK`'s 30-minute Android-enforced timeout is only renewed on playback-state
  transitions — a station playing uninterrupted for >30 min without any state change could see
  the wakelock silently expire. Low/inconsistent real-world impact (foreground service + audio
  HAL typically compensate), not fixed this pass.
- `Log.w` calls in `OfflineFirstStationRepository` aren't gated by the `isDebuggable` check used
  everywhere else in the codebase — low risk (only logs exception `.message`, no URLs/PII), but
  fixing it cleanly means threading a `Context`/`BuildConfig` dependency into a currently pure
  data-layer class, a bigger architectural change than the finding's severity warrants.
- Missing `1.json`/`2.json` schema snapshots under `core/core-database/schemas/` — Room's
  `MigrationTestHelper` can't validate `MIGRATION_1_2`/`MIGRATION_2_3` against real historical
  schemas without them. Process gap, not a runtime bug; worth a follow-up if migration test
  coverage is added.

## Round 2 (same day): feature build + verification audit

After Round 1 merged to `main`, built three things on `feat/eq-android-auto-2026-07-09`: free
EQ presets, Android Auto browse-root improvements (Continue/Surprise-me tiles,
network-error-vs-empty distinction), and a fix for a bug reported multiple times across
earlier sessions — playback continuing on the phone speaker after leaving the car. Two
adversarial verification agents then reviewed these changes independently before merge,
specifically instructed to try to disprove the fixes rather than confirm them.

### The car-disconnect bug — root cause and fix

This was the fourth fix attempt for the same complaint (prior attempts: `3df6347`,
`b717153`/`131fad5`, both already in `main`). Root-caused this pass: `onDisconnected` used to
reset `lastAutoResumeAttemptAtMs` to `0` on every disconnect so a brief AA/BT drop could
resume "instantly" on reconnect. But that timestamp is *only* ever written inside
`tryAutoResumeOnConnect()`, itself only called from a successful `onPostConnect` — so after any
real, sustained drive it's already many minutes stale by the time of a genuine disconnect,
meaning the reset provided **no actual protection** against the failure mode it was meant to
prevent: a spurious reconnect blip during the car's teardown/ignition-off sequence (common —
head units often bounce the connection once before fully dropping it) could freely call
`tryAutoResumeOnConnect()` again and resume playback on the phone speaker moments after the
user genuinely left.

Fix: a dedicated `lastDisconnectPauseAtMs` timestamp + `DISCONNECT_RESUME_GUARD_MS` (2.5s)
guard, checked independently of the older (already-broken) cooldown.

**Verified by an adversarial review agent**, which confirmed the staleness diagnosis by tracing
every write site of `lastAutoResumeAttemptAtMs`, confirmed no race window in the new
browse-root tiles, and found one real regression: a **legitimate** brief AA/BT drop while still
driving goes through the exact same `onDisconnected`→`onPostConnect` path as a real
disconnect, so it now also waits up to 2.5s before resuming instead of "instantly" — a real,
disclosed tradeoff (documented in code comments and here) rather than a silent one, accepted
because a ~2.5s delayed resume is a much smaller annoyance than the bug it replaces. The
reviewer also proposed a more robust design: `androidx.car.app`'s `CarConnection` (a debounced
OS-level car-connection-type signal) instead of inferring connection state from raw
MediaSession controller churn + a tuned timeout. Not implemented inline — it needs a new
dependency and real head-unit testing this environment can't provide — tracked in
`ROADMAP.md`/`ROADMAP.de.md` under Planned Next, bundled with the existing "Android Auto smoke
test on real head unit" item.

### Other findings from the verification pass (both fixed)

- `pickSurpriseStation()`'s empty-candidate fallback could suggest the currently-playing
  station as a "surprise" when it was the only Quick Access entry — fixed to return `null`
  instead (no tile shown) rather than a non-surprising fallback.
- `EqualizerController` wasn't released on the buffer-profile-rebuild teardown path
  (`recreatePlayerForBufferProfileIfNeeded`), only on the main `release()` path — a stale
  `Equalizer` could stay registered against a dead audio session in AudioFlinger until the next
  `attach()` implicitly cleaned it up (longer, or indefinite, if audio focus is delayed or
  playback stalls first). Fixed.
- EQ feature otherwise verified clean: thread-safety (all calls confirmed main-thread-only via
  `Dispatchers.Main.immediate`), a genuine "leaking this" NPE footgun in
  `SettingsRepository`'s granular Flow properties correctly avoided by deriving EQ reactivity
  from the existing `settingsState` instead, platform API guarding, and band-gain math (checked
  by hand for 2/3/4/5/10-band devices across all four presets) all confirmed correct.

All changes re-verified after fixes: full `gradle build` + test suite + lint + debug APK
assembly, all green.
